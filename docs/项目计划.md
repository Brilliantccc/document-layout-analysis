# 项目3：文档版面分析系统 — 项目计划与进展

## 项目概述

| 项目 | 内容 |
|------|------|
| **目标** | 实现文档版面元素检测和分类 |
| **数据集** | DocLayNet-base（6910 train / 648 val / 499 test，原始 1025×1025） |
| **下载链接** | https://huggingface.co/datasets/pierreguillou/DocLayNet-base |
| **评估指标** | mAP@[.5:.95]（论文口径）+ mAP@0.5 + 逐类 AP；见下文"目标口径的更正" |

## 实际技术栈

| 角色 | 模型 | 实现 | 许可 |
|------|------|------|------|
| 主模型 | RT-DETR-R50vd | HuggingFace `transformers`（`RTDetrForObjectDetection`） | Apache-2.0 |
| 基线 | Faster R-CNN ResNet50-FPN | torchvision | BSD-3 |

计划文档早期写的 **Detectron2 / Mask R-CNN / LayoutLMv3 从未在代码里实现过**，
现按实际情况更正。LayoutLMv3 的多模态融合需要 OCR 文本作为输入，而本项目的
`dataset.py` 只提供视觉标注，因此不做（见"未实现的部分"）。

## 发展阶段

### 阶段0：手写 DETR（已废弃）

最早实现了一版手写 DETR（ResNet50 + `nn.TransformerEncoder/Decoder` + 自写
Hungarian matching + 2D 正弦位置编码），训练到 epoch 81 时 val mAP@0.5 = **0.0253**。

加载权重实际推理后定位到三处致命 bug：

| # | Bug | 位置 | 后果 |
|---|-----|------|------|
| 1 | **双重 sigmoid**：`bbox_head` 末尾已有 `nn.Sigmoid()`，forward 里又调一次 | `model.py` 旧 54 / 91 / 113 行 | `sigmoid(sigmoid(x))` 值域被压到 **(0.5, 0.731)**，模型在数学上无法预测该区间外的坐标。实测预测框 w,h 均值全部落在 0.500~0.731，IoU≥0.5 几乎不可能 |
| 2 | **缺 no-object 损失**：CE 只对 Hungarian 匹配上的 query 计算 | 旧 225 行 | 剩下 ~80 个 query 无梯度。实测 500/500 个 query 全部以 >0.9 置信度判前景，背景类胜出 0 次，precision 崩塌 |
| 3 | **class_head off-by-one**：`num_classes + 1` = 13 维，但 `num_classes=12` 已含背景 | 旧 47 行 | 背景索引用 12，索引 11 是死单元 |

设计层面还有两个硬伤：`num_queries=100` 装不下数据（**34% 的图标注框超过 100 个**，
最多 1162 个），以及手写版没有 query selection 和多尺度特征。

**结论**：该实现和对应权重全部丢弃。这次失败的教训直接催生了
`verify_pipeline.py` —— 三个 bug 都是"训练能正常跑完、指标极低"的静默错，
只看 loss 曲线发现不了。

### 阶段1：Faster R-CNN 基线（✅ 完成）

torchvision Faster R-CNN ResNet50-FPN，`GeneralizedRCNNTransform` 默认
`min_size=800` → 实际输入 800×800。**实测 mAP@0.5 0.695 / mAP@[.5:.95] 0.477。**

当初预期的"没有 query 上限、在密集页面上可能反超"没有成立 —— 去重后每页真实只有
13.2 个框（不是污染数据里的 p99=453），所以 query 数量从来不是瓶颈。FRCNN 真正的优势
在**最小的那两类**（Footnote 0.474 vs 0.226、Picture 0.675 vs 0.419），原因很可能是
它的 FPN 从 stride 4 起，而 RT-DETR 的 `feat_strides=[8,16,32]` 最细一层就粗一倍。

### 阶段2：RT-DETR 主模型（✅ 完成）

RT-DETR-R50vd，从 `PekingU/rtdetr_r50vd_coco_o365`（COCO 53.1% AP / O365 55.3% AP）
微调。选它的理由：

- DETR 家族，端到端无 NMS，与本项目"阶段3 DETR"的原计划一致
- 有 COCO+Objects365 预训练，6910 张小数据集上几十 epoch 即可收敛
- 数据本来就是 COCO 格式，`RTDetrImageProcessor` 可直接消费，零转换成本
- Apache-2.0，与项目 MIT 许可兼容（对比 ultralytics 的 AGPL-3.0）

### 结果（test 集 499 页 / 6,349 框，`evaluate.py`）

| 模型 | 输入 | mAP@0.5 | mAP@[.5:.95] | mAP@0.75 |
|------|------|---------|--------------|----------|
| RT-DETR-R50vd | 1024 | 0.626 | **0.491** | 0.533 |
| Faster R-CNN R50-FPN | 800 | 0.695 | **0.477** | 0.531 |

两个模型基本打平。逐类 AP@0.5（test 样本数见括号）：

| 类别 | RT-DETR | FRCNN |
|------|---------|-------|
| Text (3002) | **0.765** | 0.736 |
| List-item (962) | 0.583 | **0.614** |
| Section-header (873) | 0.757 | **0.780** |
| Page-footer (408) | 0.850 | **0.882** |
| Page-header (311) | 0.616 | **0.784** |
| Table (252) | 0.740 | **0.773** |
| Formula (150) | **0.794** | 0.694 |
| Caption (149) | 0.467 | **0.574** |
| Picture (143) | 0.419 | **0.675** |
| Title (52) | **0.669** | 0.657 |
| Footnote (47) | 0.226 | **0.474** |

差距集中在 `Footnote` / `Picture`，很可能源于特征层数：torchvision FPN 从 stride 4 起，
RT-DETR 的 `feat_strides=[8,16,32]` 最细一层就粗一倍。

### 阶段3：消融与调优（待做）

→ 加 EMA（HF 未实现，需自己包一层）→ 换 `PekingU/rtdetr_v2_r50vd`。

## 数据的关键事实（实测，决定了超参选择）

### ⚠ 标注被复制了多份（最重要的一条）

`pierreguillou/DocLayNet-base` 的转换里标注大量重复：train 的 681,481 个标注去重后
只剩 **91,136** 个（86.6% 重复），其中 Table 98.0% / Formula 96.7% / Picture 94.4% /
Text 86.6% 是重复，而 Page-footer 只有 24.1%。有一页的 929 个 Table 框完全一致。

**这是第一版训练 mAP 只有 0.25 的根因。** 不去重时同一位置堆着几百个相同 GT，模型给
1 个框只能匹配 1 个、其余全算漏检，该类 AP 被压到接近 0 —— 实测 FRCNN / RT-DETR 的
Table AP 只有 0.01 / 0.34，而重复最少的 Page-footer 达 0.69 / 0.41。**两个完全不同的
架构（torchvision FRCNN + ImageNet 归一化 vs RT-DETR + `do_normalize=False`）给出同样的
天花板和类间排序**，正是"问题在 GT 而不在模型"的铁证。

`dataset._build_gt_index` 已按 (x,y,w,h,类别) 去重。**任何数据统计都必须先去重**，
否则结论会全错（第一版的尺寸分析和框数分析就是这样得出错误结论的）。

### 去重后的真实分布

- 每页标注框数：**平均 13.2，最多 103**（不是第一版误报的 98.6 / 1162）
  → 真实数据量下 `num_queries=300` 绰绰有余，**不存在 query 上限问题**
- 类别分布：Text 47.18% / List-item 17.15% / Section-header 12.99% /
  Page-footer 6.67% / Page-header 5.38% / Table 3.28% / Formula 2.23% /
  Caption 2.07% / Picture 2.04% / Footnote 0.54% / Title 0.48%
  （与 DocLayNet 论文的分布一致，第一版误报的 "Table 22%" 是重复造成的）
- **短边 <32px 的框占比：640 → 70.0%，800 → 62.2%，1024 → 56.4%**
  → **这个任务的主体就是小目标检测**，分辨率是最主要的杠杆，比超参重要
- `Footnote`(0.54%) / `Title`(0.48%) 样本极少，AP 方差大会拖累均值

**结论**：mAP 是 11 类等权平均，小目标占多数且分辨率是主要杠杆 → 优先上 1024
（原生分辨率，零插值损失），其次才是调超参。

## 关于"mAP@0.5 > 0.90"这个目标口径的更正

项目早期把目标写成"mAP@0.5 > 0.90"，是从 DocLayNet 论文的基准数字推的 —— 但**口径错了**。

论文 Table 2 的标题是 *"Prediction performance (mAP@0.5-0.95) of object detection
networks on DocLayNet test set"*，即 **mAP@[.5:.95]**（COCO 标准，10 个 IoU 阈值取平均），
不是 mAP@0.5。论文基线：

| 模型 | mAP@[.5:.95] |
|------|--------------|
| Mask R-CNN R50 | 0.724 |
| Mask R-CNN R101 | 0.735 |
| Faster R-CNN R101 | 0.734 |
| YOLOv5x6 | 0.768 |
| 人类标注一致性 | 0.82 ~ 0.83 |

（早期还引用过"Faster R-CNN R50 = 0.718"，那是把 Table 2 里某个**逐类**数值当成了
整体 mAP@[.5:.95]，已撤回。）

**可比的正确目标应该是 `mAP@[.5:.95] ≥ 0.70`**，而不是 mAP@0.5 ≥ 0.90。

### 实测差距的主因：数据量差 10 倍

论文基线的训练集是 69,375 页（完整 DocLayNet），而本项目用的
`pierreguillou/DocLayNet-base` 恰好是它的 1/10：

```
论文       69375 / 6489 / 4994   (train/val/test)
base 子集   6910 /  648 /  499
```

数据量差 10 倍、backbone 是 R50 对 R101 —— 实测 0.491 vs 0.734 的差距里，数据量占主导，
不是实现问题。参考上界：Docling 的 Heron-101（RT-DETRv2-R101，15 万文档）在原始
DocLayNet 上是 0.699。

### 评估口径

同时报 mAP@0.5、mAP@[.5:.95] 和逐类 AP 表，逐类 AP 要**标注 test 样本数**
（`Footnote` 只有 47 个框、`Title` 52 个，单个数波动很大）。

**交付数字以 `evaluate.py`（pycocotools）为准。** `train.py` 的 `compute_map`
系统性低报：RT-DETR 上给 ~0.54 而标准口径 0.626（差 0.09），FRCNN 上只差 0.012。
原因是标准口径按 (图像, 类别) 截断前 100 个框，而 RT-DETR 的 300 个 query 会集中输出到
每页的主导类上，被截掉的全是低分 FP。

## 未实现的部分

- **LayoutLMv3 多模态融合**：需要 OCR 文本 + 位置三元组作为输入。本项目的
  `dataset.py` 只有视觉标注，要做得先接一个 OCR 引擎（项目1 有现成的识别模型
  可以复用），再改造 dataset 输出 token 序列。属于额外工作量，不在当前范围。
- **Mask R-CNN**：原计划提到了，但从 DocLayNet 论文的结论看，Mask 分支相对
  Faster R-CNN 没有 mAP 收益（0.724 vs 0.718），不值得为此换框架。

## 训练流程

```bash
python verify_pipeline.py --overfit 8      # 1) 先验证 pipeline（必做）
python train.py --detector rtdetr --epochs 60 --img_size 800 --batch_size 8   # 2) 主模型

python evaluate.py --weights runs/rtdetr/v1/best.pth --split test             # 4) 评估
```
